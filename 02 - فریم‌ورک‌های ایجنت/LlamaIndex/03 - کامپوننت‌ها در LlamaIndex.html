خانه/۰۲ — فریم‌ورک‌های ایجنت/LlamaIndex/کامپوننت‌ها در LlamaIndex

کامپوننت‌ها در LlamaIndex چیستند؟

آلفرد، پیشخدمت ایجنت مفید ما از فصل اول را به یاد دارید؟ برای اینکه آلفرد بتواند به‌طور مؤثر به ما کمک کند، باید درخواست‌های ما را بفهمد و اطلاعات مرتبط را برای تکمیل وظایف آماده، پیدا و استفاده کند. اینجاست که کامپوننت‌های LlamaIndex وارد می‌شوند.

اگرچه LlamaIndex کامپوننت‌های فراوانی دارد، ما به‌طور مشخص روی کامپوننت QueryEngine تمرکز می‌کنیم. چرا؟ چون می‌توان از آن به‌عنوان یک ابزار RAG (تولید تقویت‌شده با بازیابی | Retrieval-Augmented Generation) برای ایجنت استفاده کرد.

پس RAG چیست؟ LLMها روی حجم عظیمی از داده آموزش می‌بینند تا دانش عمومی یاد بگیرند. با این حال، ممکن است روی داده‌های مرتبط و به‌روز آموزش ندیده باشند. RAG این مشکل را با پیدا کردن و بازیابی اطلاعات مرتبط از داده‌های شما و دادن آن به LLM حل می‌کند.

حالا به نحوه‌ی کار آلفرد فکر کنید:

  1. شما از آلفرد می‌خواهید در برنامه‌ریزی یک مهمانی شام کمک کند
  2. آلفرد باید تقویم شما، ترجیحات غذایی‌تان و منوهای موفق قبلی را بررسی کند
  3. QueryEngine به آلفرد کمک می‌کند این اطلاعات را پیدا کند و برای برنامه‌ریزی مهمانی شام از آن‌ها استفاده نماید

این موضوع QueryEngine را به یک کامپوننت کلیدی برای ساخت گردش‌کارهای Agentic RAG در LlamaIndex تبدیل می‌کند. همان‌طور که آلفرد برای مفید بودن باید در اطلاعات خانه‌ی شما جستجو کند، هر ایجنتی به راهی برای پیدا کردن و فهمیدن داده‌های مرتبط نیاز دارد. QueryEngine دقیقاً همین قابلیت را فراهم می‌کند.

اکنون کمی عمیق‌تر به کامپوننت‌ها بپردازیم و ببینیم چگونه می‌توانید کامپوننت‌ها را ترکیب کنید تا یک پایپ‌لاین RAG بسازید.

ساخت یک پایپ‌لاین RAG با استفاده از کامپوننت‌ها

💡 نکته

می‌توانید کد را در این نوت‌بوک دنبال کنید که با Google Colab قابل اجراست.

RAG پنج مرحله‌ی کلیدی دارد که خود بخشی از اغلب اپلیکیشن‌های بزرگ‌تری هستند که خواهید ساخت. این مراحل عبارت‌اند از:

  1. بارگذاری (Loading): یعنی آوردن داده‌هایتان از جایی که قرار دارند، چه فایل‌های متنی، PDF، وب‌سایتی دیگر، پایگاه داده یا API، به درون گردش‌کار شما. LlamaHub صدها ادغام برای انتخاب ارائه می‌دهد.
  2. ایندکس‌سازی (Indexing): یعنی ساختن یک ساختار داده که امکان پرس‌وجو روی داده‌ها را فراهم کند. برای LLMها این تقریباً همیشه به معنای ساخت امبدینگ‌های برداری (Vector Embeddings) است؛ نمایش‌های عددی از معنای داده. ایندکس‌سازی همچنین می‌تواند به راهبردهای متادیتایی متعدد دیگری اشاره داشته باشد تا پیدا کردن دقیق داده‌های مرتبط با زمینه، بر اساس ویژگی‌ها، آسان شود.
  3. ذخیره‌سازی (Storing): پس از ایندکس شدن داده‌ها، می‌خواهید ایندکس و سایر متادیتاها را ذخیره کنید تا نیازی به ایندکس مجدد نباشد.
  4. پرس‌وجو (Querying): برای هر راهبرد ایندکس‌سازی، راه‌های زیادی برای استفاده از LLMها و ساختارهای داده‌ی LlamaIndex جهت پرس‌وجو وجود دارد، از جمله زیرکوئری‌ها (Sub-queries)، کوئری‌های چندمرحله‌ای و راهبردهای ترکیبی (Hybrid).
  5. ارزیابی (Evaluation): گام حیاتی در هر جریان، بررسی میزان اثربخشی آن نسبت به راهبردهای دیگر یا هنگام اعمال تغییرات است. ارزیابی معیارهای عینی‌ای از دقت، وفاداری و سرعت پاسخ‌های شما به کوئری‌ها ارائه می‌دهد.

در ادامه می‌بینیم چگونه می‌توانیم این مراحل را با استفاده از کامپوننت‌ها بازتولید کنیم.

بارگذاری و امبد کردن اسناد

همان‌طور که گفته شد، LlamaIndex می‌تواند روی داده‌های خودتان کار کند، اما پیش از دسترسی به داده‌ها باید آن‌ها را بارگذاری کنیم. سه روش اصلی برای بارگذاری داده در LlamaIndex وجود دارد:

  1. SimpleDirectoryReader: یک لودر داخلی برای انواع فایل‌ها از یک پوشه‌ی محلی.
  2. LlamaParse: ابزار رسمی LlamaIndex برای پارس PDF که به‌صورت یک API مدیریت‌شده در دسترس است.
  3. LlamaHub: رجیستری صدها کتابخانه‌ی بارگذاری داده برای دریافت داده از هر منبعی.
💡 نکته

با لودرهای LlamaHub و پارسر LlamaParse برای منابع داده‌ی پیچیده‌تر آشنا شوید.

ساده‌ترین راه بارگذاری داده، SimpleDirectoryReader است. این کامپوننت همه‌کاره می‌تواند انواع فایل‌ها را از یک پوشه بارگذاری کند و آن‌ها را به آبجکت‌های Document تبدیل کند که LlamaIndex بتواند با آن‌ها کار کند. بیایید ببینیم چگونه می‌توانیم از SimpleDirectoryReader برای بارگذاری داده از یک پوشه استفاده کنیم.

from llama_index.core import SimpleDirectoryReader

reader = SimpleDirectoryReader(input_dir="path/to/directory")
documents = reader.load_data()

پس از بارگذاری اسناد، باید آن‌ها را به قطعات کوچک‌تری به نام آبجکت‌های Node بشکنیم. یک Node فقط یک قطعه (Chunk) از متن سند اصلی است که کار کردن با آن برای هوش مصنوعی آسان‌تر است، و در عین حال ارجاع‌هایی به آبجکت Document اصلی دارد.

IngestionPipeline با دو تبدیل (Transformation) کلیدی به ما در ساخت این Nodeها کمک می‌کند:

  1. SentenceSplitter اسناد را با تقسیم‌کردن در مرزهای طبیعی جمله‌ها به قطعات قابل‌مدیریت می‌شکند.
  2. HuggingFaceEmbedding هر قطعه را به امبدینگ‌های عددی تبدیل می‌کند؛ نمایش‌های برداری‌ای که معنای مفهومی را به شکلی که هوش مصنوعی بتواند کارآمد پردازش کند در خود دارند.

این فرایند به ما کمک می‌کند اسنادمان را به شکلی سازمان‌دهی کنیم که برای جستجو و تحلیل مفیدتر باشد.

from llama_index.core import Document
from llama_index.embeddings.huggingface import HuggingFaceEmbedding
from llama_index.core.node_parser import SentenceSplitter
from llama_index.core.ingestion import IngestionPipeline

# ساخت پایپ‌لاین به‌همراه تبدیل‌ها
pipeline = IngestionPipeline(
    transformations=[
        SentenceSplitter(chunk_overlap=0),
        HuggingFaceEmbedding(model_name="BAAI/bge-small-en-v1.5"),
    ]
)

nodes = await pipeline.arun(documents=[Document.example()])

ذخیره‌سازی و ایندکس‌سازی اسناد

پس از ساخت آبجکت‌های Node، باید آن‌ها را ایندکس کنیم تا قابل جستجو شوند، اما پیش از آن به جایی برای ذخیره‌ی داده‌هایمان نیاز داریم.

از آنجا که از یک ingestion pipeline استفاده می‌کنیم، می‌توانیم مستقیماً یک vector store را به پایپ‌لاین وصل کنیم تا آن را پر کند. در این مثال از Chroma برای ذخیره‌ی اسنادمان استفاده می‌کنیم.

نصب ChromaDB

همان‌طور که در بخش LlamaHub معرفی شد، می‌توانیم vector store مربوط به ChromaDB را با دستور زیر نصب کنیم:

pip install llama-index-vector-stores-chroma
import chromadb
from llama_index.vector_stores.chroma import ChromaVectorStore

db = chromadb.PersistentClient(path="./alfred_chroma_db")
chroma_collection = db.get_or_create_collection("alfred")
vector_store = ChromaVectorStore(chroma_collection=chroma_collection)

pipeline = IngestionPipeline(
    transformations=[
        SentenceSplitter(chunk_size=25, chunk_overlap=0),
        HuggingFaceEmbedding(model_name="BAAI/bge-small-en-v1.5"),
    ],
    vector_store=vector_store,
)
💡 نکته

نمای کلی انواع مختلف vector storeها را می‌توانید در مستندات LlamaIndex ببینید.

اینجاست که امبدینگ‌های برداری وارد می‌شوند: با امبد کردن هم کوئری و هم Nodeها در یک فضای برداری مشترک، می‌توانیم تطبیق‌های مرتبط را پیدا کنیم. VectorStoreIndex این کار را برای ما انجام می‌دهد و از همان مدل امبدینگی که هنگام ingestion استفاده کردیم بهره می‌برد تا سازگاری تضمین شود.

بیایید ببینیم چگونه این ایندکس را از vector store و امبدینگ‌هایمان بسازیم:

from llama_index.core import VectorStoreIndex
from llama_index.embeddings.huggingface import HuggingFaceEmbedding

embed_model = HuggingFaceEmbedding(model_name="BAAI/bge-small-en-v1.5")
index = VectorStoreIndex.from_vector_store(vector_store, embed_model=embed_model)

همه‌ی اطلاعات به‌طور خودکار درون آبجکت ChromaVectorStore و مسیر پوشه‌ی داده‌شده پایدار (Persist) می‌شوند.

عالی! اکنون که می‌توانیم ایندکس خود را به‌سادگی ذخیره و بارگذاری کنیم، بیایید ببینیم چگونه می‌توان به روش‌های مختلف از آن پرس‌وجو کرد.

پرس‌وجو از یک VectorStoreIndex با پرامپت‌ها و LLMها

پیش از اینکه بتوانیم از ایندکس خود پرس‌وجو کنیم، باید آن را به یک رابط پرس‌وجو (Query Interface) تبدیل کنیم. رایج‌ترین گزینه‌های تبدیل عبارت‌اند از:

  • as_retriever: برای بازیابی پایه‌ی اسناد؛ فهرستی از آبجکت‌های NodeWithScore را همراه با امتیازهای شباهت برمی‌گرداند.
  • as_query_engine: برای تعامل‌های تک‌سوال و تک‌جواب؛ یک پاسخ نوشتاری برمی‌گرداند.
  • as_chat_engine: برای تعامل‌های مکالمه‌ای که حافظه را در طول چند پیام حفظ می‌کنند؛ با استفاده از تاریخچه‌ی چت و زمینه‌ی ایندکس‌شده، پاسخ نوشتاری برمی‌گرداند.

ما روی query engine تمرکز می‌کنیم، چون برای تعامل‌های ایجنت‌گونه رایج‌تر است. همچنین یک LLM را برای تولید پاسخ به query engine می‌دهیم.

from llama_index.llms.huggingface_api import HuggingFaceInferenceAPI

llm = HuggingFaceInferenceAPI(model_name="Qwen/Qwen2.5-Coder-32B-Instruct")
query_engine = index.as_query_engine(
    llm=llm,
    response_mode="tree_summarize",
)
query_engine.query("What is the meaning of life?")
# The meaning of life is 42

پردازش پاسخ

در پشت صحنه، query engine فقط از LLM برای پاسخ به سوال استفاده نمی‌کند، بلکه یک ResponseSynthesizer را هم به‌عنوان راهبردی برای پردازش پاسخ به کار می‌گیرد. باز هم این بخش کاملاً قابل‌سفارشی‌سازی است، اما سه راهبرد اصلی وجود دارد که به‌صورت پیش‌فرض خوب کار می‌کنند:

  • refine: با گذر ترتیبی از هر قطعه‌ی متنِ بازیابی‌شده، پاسخ را می‌سازد و اصلاح می‌کند. این کار برای هر Node یا قطعه‌ی بازیابی‌شده یک فراخوانی جداگانه‌ی LLM انجام می‌دهد.
  • compact (پیش‌فرض): مشابه refine است، اما قطعات را از قبل به هم می‌چسباند و در نتیجه فراخوانی‌های LLM کمتری انجام می‌شود.
  • tree_summarize: با گذر از هر قطعه‌ی متنِ بازیابی‌شده و ساخت یک ساختار درختی از پاسخ، یک پاسخ دقیق می‌سازد.
💡 نکته

با API ترکیب سطح‌پایین (Low-level Composition API) کنترل دقیقی روی گردش‌کارهای پرس‌وجوی خود به‌دست آورید. این API به شما اجازه می‌دهد هر مرحله از فرایند پرس‌وجو را مطابق نیازهای دقیق خود سفارشی و تنظیم کنید و با Workflowها نیز ترکیب عالی‌ای می‌سازد.

مدل زبانی همیشه به شکل قابل‌پیش‌بینی عمل نمی‌کند، پس نمی‌توانیم مطمئن باشیم پاسخ دریافتی همیشه درست است. می‌توانیم این مشکل را با ارزیابی کیفیت پاسخ مدیریت کنیم.

ارزیابی و مشاهده‌پذیری (Evaluation and Observability)

LlamaIndex ابزارهای ارزیابی داخلی برای سنجش کیفیت پاسخ ارائه می‌دهد. این ارزیاب‌ها با بهره‌گیری از LLMها پاسخ‌ها را در ابعاد مختلف تحلیل می‌کنند. بیایید سه ارزیاب اصلی موجود را ببینیم:

  • FaithfulnessEvaluator: وفاداری پاسخ را با بررسی اینکه آیا پاسخ توسط زمینه (Context) پشتیبانی می‌شود ارزیابی می‌کند.
  • AnswerRelevancyEvaluator: ارتباط پاسخ را با بررسی اینکه آیا پاسخ به سوال مرتبط است ارزیابی می‌کند.
  • CorrectnessEvaluator: صحت پاسخ را با بررسی اینکه آیا پاسخ درست است ارزیابی می‌کند.
💡 نکته

می‌خواهید درباره‌ی مشاهده‌پذیری و ارزیابی ایجنت بیشتر بدانید؟ سفر خود را با بخش جایزه ۲ (Bonus Unit 2) ادامه دهید.

from llama_index.core.evaluation import FaithfulnessEvaluator

query_engine = # از بخش قبل

حتی بدون ارزیابی مستقیم هم می‌توانیم از طریق مشاهده‌پذیری (Observability) به عملکرد سیستم‌مان بینش پیدا کنیم. این موضوع به‌ویژه وقتی گردش‌کارهای پیچیده‌تری می‌سازیم و می‌خواهیم بفهمیم هر کامپوننت چگونه عمل می‌کند، مفید است.

نصب LlamaTrace

همان‌طور که در بخش LlamaHub معرفی شد، می‌توانیم callback مربوط به LlamaTrace از Arize Phoenix را با دستور زیر نصب کنیم:

pip install -U llama-index-callbacks-arize-phoenix

علاوه بر این، باید متغیر محیطی PHOENIX_API_KEY را روی کلید API حساب LlamaTrace خود تنظیم کنیم. برای دریافت آن:

  • در LlamaTrace یک حساب بسازید
  • در تنظیمات حساب خود یک کلید API تولید کنید
  • از کلید API در کد زیر برای فعال‌سازی ردیابی (Tracing) استفاده کنید
import llama_index
import os

PHOENIX_API_KEY = "<PHOENIX_API_KEY>"
os.environ["OTEL_EXPORTER_OTLP_HEADERS"] = f"api_key={PHOENIX_API_KEY}"
llama_index.core.set_global_handler(
    "arize_phoenix",
    endpoint="https://llamatrace.com/v1/traces"
